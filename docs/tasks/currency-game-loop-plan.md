## 問題・解決策・結論

問題: 現行機能は採取・搬送・保管・加工までで、収益と設備への再投資を結ぶルールがない。
解決策: 採取資源を初期配置の特異点セルへ搬送して換金し、通貨を設備の設置・個別強化・全体スキルへ使う。
結論: 残高と取引、特異点、設置、能力計算、個別強化、スキル、表示、統合検証の順で実装する。計画作成時の成果は計画とpendingタスクの登録。現在の進捗はタスクリストを参照する。

## 採用仕様

| 対象 | 仕様と判断理由 |
| --- | --- |
| 進行 | 採取 → 搬送 → 特異点で換金 → 設置・強化・スキル購入 → 生産拡大。全状態は一プレイセッションの所有者が保持し、再開始で初期化する。永続セーブは今回の実装対象に含めない。 |
| 通貨 | 単一の共有残高。非負の64bit整数でchecked計算し、入金予定額と支出予約額を別に保持する。換金単価・価格は正の整数で定義し、残高上限や不足時は操作前に拒否する。ScriptableObjectは設定入力、残高・レベル・取得状態は実行時状態。 |
| 初期条件 | 初期残高100、木材・石材の単価1。抽出設備20、通常コンベア5、搬出コンベア5、交差10、保管15、加工30。その他の資源は売価定義がある場合だけ換金可能。調整値は設定へ集約する。 |
| 特異点 | フィールド中央 `(gridSize/2, gridSize/2)` に1基を初期配置し、四方向から受け入れる消費専用セル。削除・上書き・追加購入を禁止する。設定・位置・単一性を検証し、登録後に接続初期化する。 |
| 初回換金 | 中央周辺に木材資源、抽出設備の配置候補、搬出・通常コンベア用の空き経路を確保する。必要な設備1組と経路の総額を100以下にし、再生成でも成立を検証する。設置前のプレビューに費用を表示する。 |
| 設置・撤去 | 空セルへの設備設置を課金し、回転と選択は無料。資源セルと特異点は保護する。設備撤去は無料・返金なしで、在庫と保持IDの処分は既存削除契約に従う。範囲操作はドラッグ開始から終端の座標順に1セルずつ確定し、不足・失敗で停止する。成功した分の費用・個数を表示する。 |
| 個別強化 | 対象設備のレベルは1〜3。次レベルへの費用は設置価格×現在レベル、最大レベルでは購入不可。抽出量、搬送量、保管容量、加工入出力容量のうち設備が持つ値を基礎値×レベルにする。同じインスタンスを強化し、座標・方向・在庫・予約・稼働状態を維持する。 |
| スキルツリー | 通貨で取得する共有ツリー。根「基礎研究」50から「採取効率」「搬送効率」「保管効率」へ分岐し、各枝はI=50・II=100、IIはIを前提とする。根は枝の解禁、枝は段階ごとに該当能力+25%。取得は一度だけ、依存は固定ノードuidで管理し、循環・欠落・重複を定義検証で拒否する。 |
| 全体効果 | 全体とは設置済み・後から設置する全セルへの同一の能力規則を指す。採取効率は抽出量、搬送効率はコンベア系の搬送量、保管効率は抽出在庫・保管・加工入出力容量に適用する。能力を持たない空セル・資源セル・特異点は変化しない。 |
| 能力合成 | 基礎値×個別レベル×(100+該当枝の加算率)/100を整数で切り捨て、正の最小値1を保証する。抽出在庫容量にも個別レベルを適用する。定義と最大合成値を事前検証し、int上限超過を拒否する。設定を直接書き換えず、有効値を読み取る。 |
| 効果の反映時点 | 能力更新後の新しい抽出周期・搬送試行から数量を使う。稼働中の抽出量・搬送量・予約・加工計画は開始時の値を固定する。容量は即時増加し、在庫と予約を減らさない。抽出中断時の未完了進捗破棄は既存仕様どおり。 |

## 現行設計との接続と搬送の不変条件

[設計方針](../design/architecture-guidelines.md) と [配置規則](../design/script-organization.md) に従う。新規機能はEconomy・ProgressionのDomain/Application/Adapter/Definitionsへ置く。Domainは数量・価格・能力・前提条件の計算、Applicationは取引と実行時状態、Adapterはセル・シーン・UIとの接続を担う。構成入口から必要な契約を渡し、未使用ServiceLocatorを前提にしない。

- 接点は [搬送状態の契約](../spec/resource-transfer-state.md) の固定IdentityとIsAlive、`IContainableApplication` の全量予約・確定・取消を使う。特異点はConnectableCellBaseAdapterを使い、共有Coordinatorの演出成功後のStoreResourceで換金する。
- StoreResourceはvoidで、予約Tokenは呼出し前にCommittedになるため、確定時の残高上限エラーを後から取り消せない。予約時に種別・量・単価・換金額を固定し、他の入金予約も含め残高上限の余地を確保する。支出予約の取消でも入金余地を破らない計算にする。確定処理は予約額の入金と予約解除を通知前に一組で更新し、成立済み予約の確定を失敗させない。
- StoreResourceへ種別・予約IDが渡らない既存契約に合わせ、特異点は入力方向ごとに未確定予約1件を保持する。同方向の追加予約は拒否し、四方向の異種資源は独立して扱う。確定・取消は方向、数量、取消時の種別を照合する。
- 取消・演出失敗・切断では入金せず、上限用の予約額を一度だけ解除する。非アクティブ化時は接続取消を先に完了し、再有効化で再接続する。寿命終了時の受け取り側予約解放も実装側が担う。Identity/IsAliveの既存意味を維持する。
- 特異点は資源を消費し、搬送IDを再利用先へ引き継がない。成功終端の資源データと表示返却は既存所有者・Coordinator経路へ任せる。取消時の送り元資源保持、送り元削除時の処分を維持する。
- 設置・強化・スキル購入はApplicationで支出を予約し、対象・価格・前提を確定直前に再確認する。設置は旧セルを破棄する前に新セルを準備し、登録・初期化失敗ならグリッドと支出予約を復元する。成功時だけ支出を確定し、通知は状態確定後に行う。連打・再入・同じ取引の反復は一度だけ成功させる。
- 新セルの状態表示は [UI契約](../spec/cell-status-ui.md) のCreateCustom入口へ専用Adapterの読み取り関数を渡す。UIは残高や能力を表示し、購入命令をApplicationへ渡す。

## 検証・記録と再開

既存 `ResourceReservationVerifierEditor.Run`、`ResourceTransferVerifierEditor.Run` と、抽出・加工・UIの該当検証入口を再利用する。新しい経済・成長の境界検証は既存Editor検証基盤へ加える。最終統合で `GridFieldGeneratorVerifierEditor.RunPlayerBuild` を使い、動作検証とビルドの結果を分ける。UIは表示値・操作・購読寿命をテストで確認し、目視は文字の重なりや操作の分かりやすさへ絞る。

計画作成時の検証対象は文書とChronos登録であり、Unity実行検証は各実装タスクの完了条件である。計画作成ではコード・Prefab・シーンを変更していない。実装後は該当するdocs/specの現行仕様、current-architectureの機能参照、タスク状態とコード版・実行条件・結果を更新する。

再開時は最新inventoryとgit差分を確認し、現在の依頼と依存順に沿って着手する。価格・初期経路は上記を初期値として実装し、調整後も初回換金成立の検証を維持する。
